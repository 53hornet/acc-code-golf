What's in the image

The image is 792 × 404 pixels (319,968 in total), but it holds much less information than that suggests:

  • Only 3 gray values are used: black (0), the darker gray of "azara" (80) and the lighter gray of the leaf, "r" and "healthcare" (133).
  • 89% of the pixels are black background.
  • The two grays never touch. There's always black between them. So the real question for each pixel is "background or not?", and the shade is almost always obvious from the neighbors.
  • Letters repeat. "azara" has three a's, and "healthcare" has two each of h, e and a. Some copies are almost pixel-identical.

The core idea: predict, then pay only for surprises

The compressor visits the pixels one at a time. For each one, a model looks at everything already decoded and predicts a probability, for example "97% sure this pixel is background". An arithmetic coder turns those predictions into bits: a confident, correct guess costs a tiny fraction of a bit, while a surprise costs several bits. The decoder runs exactly the same model, makes exactly the same predictions, and so can read the bits back.

How the arithmetic coder spends bits

Each pixel shrinks the coder's current range to the share its prediction gave the real outcome. Narrowing by half costs 1 bit.

So the whole game is making better predictions. Every idea below is just a better way to guess the next pixel.

The pipeline

1PaletteMap the 3 grays to indices. The most common, black, becomes background (0).
2OrientationTry all 8 flips and rotations, and keep whichever compresses best.
3Find copiesSpot letters that nearly match an earlier one and note where the copy is.
4PredictFor each pixel: background or not? Then which gray?
5CodeArithmetic-code every decision, header included, into one stream.

1. Looking at the neighbors

The simplest predictor is the pattern of already-decoded pixels around the current one. We keep five nested neighborhoods, from the 6 nearest pixels out to 36. Each one keeps its own count of what came next every time that exact pattern appeared before. Small neighborhoods learn fast; large ones capture the shapes of curves, but only once they've seen enough examples.

The five neighborhood patterns

Each shade adds one ring of pixels around the current pixel (?). Pixels to its right on the current row aren't decoded yet, so they can't be used.

2. Following edges

Letters are smooth curves, so an edge drifts predictably from one row to the next. For the nearest edge in the row above, the model follows it back up to four rows and records how far it moved each time, such as "left 1, then left 2, then left 2". That history, plus how far the current pixel is from where the edge should land, becomes another context. This is how the model learns curvature without needing a huge neighborhood.

Predicting where an edge lands

The edge moved −1, −2, −2 over the last rows, so it's expected 2 pixels further left: right at the current pixel.

3. Copying repeated letters

Before coding, the compressor looks for shapes that nearly match an earlier one: same size, and few differing pixels at the best alignment. For each match it sends a small rectangle and an offset. Inside that rectangle the model also gets to look at the matching pixels of the earlier copy, so a near-duplicate costs almost nothing.

4. Mixing all the predictions

That gives 13 separate predictions for every pixel: five neighborhood patterns, five edge-based contexts and three copy-based contexts. A small learned mixer (logistic mixing, the core of the PAQ family of compressors) combines them into one probability. It learns as it goes which inputs to trust in which situation. One set of weights is picked by the 6-pixel neighborhood, another by how well the reference letter agrees locally, and the two results are averaged.

From 13 guesses to one probability

Each input doesn't use its raw counts directly. A context seen "3 times, always background" is mapped through a learned table to a probability, so the model learns from experience how much to trust a pattern it has only seen a few times. On a small image, where most patterns are rare, this mattered a lot.

5. Choosing the scan direction

Where the coder starts and which way it scans changes what it knows at each pixel. The encoder simply tries all 8 flips and rotations in parallel and keeps the smallest. Here the winner scans column by column, from the right edge. That's also why the 3rd "a" is the one coded from scratch.

How we got here

Each idea was first tested by adding up its ideal bit cost in a quick prototype, and kept only if the number went down. The figures below cover the shape part only ("background or not?"); the final file adds the gray choice, the header and the copy rectangles.

A few things we tried didn't help: fitting edges with a curve (second-order extrapolation) was worse than a straight line, and giving the mixer a separate input for every copy offset made the other letters more expensive. The copies only paid off once each one was limited to its own rectangle.

Built to survive Part 2

  • Nothing about this image is hard-coded. Size, max value, palette, scan order and letter copies are all worked out from the input and stored in the header.
  • Any number of grays, including 16-bit images with values up to 65535. Comments are allowed anywhere.
  • Color took one small change. For plain-text P3, each RGB pixel is packed into a single number, so the palette and coder work unchanged. One header bit records gray or color. azara.ppm also has just 3 colors (black, gray 75 81 89 and green 13 172 102), so it compresses to 550 bytes, only 9 more than the gray version.
  • Deterministic decoding. Probabilities pass through integer lookup tables, so the decoder makes bit-identical predictions on any machine.
  • One code path. A single function walks the pixels for both compressing and decompressing, so the two can't drift apart.

Ideas left on the table

  • The copy rectangles cost 40 bytes (about 8 per letter). Coding them relative to the letter they copy could save most of that.
  • The settings were tuned on this one image. A different image might prefer other learning rates or neighborhood sizes. The encoder could try a few and record the choice in the header.
  • Binary P5/P6 input would only take a few more lines to support.
